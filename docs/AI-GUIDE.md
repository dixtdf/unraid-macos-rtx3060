# AI 教材：如何使用这份安装方案

这份教材让 AI 能从仓库直接取得背景，接手新的安装、既有 VM 排障或方案维护。它不是授权凭据，也不是要求无条件执行全部脚本。先根据用户当前目标确定任务范围。

## 先读什么

入口是根目录 [AGENTS.md](../AGENTS.md)，整体说明在 [README](../README.md)，机器索引在 [ai/knowledge.json](../ai/knowledge.json)，参考实测在 [results/observed-2026-10-09.json](../results/observed-2026-10-09.json)。

维护后的驱动结果见 [1.9.0 实测](../results/observed-2026-10-11-1.9.0.json)及[升级章节](09-driver-upgrade-1.9.0.md)。准备升 1.10.0 时先读[兼容性审查](10-driver-upgrade-1.10.0.md)：RTX 3060 不再注册硬编码器，当前 GlideBeam 没有软件编码回退。读取官方变更并确认功能取舍后再升级，不能把 1.9.0 的 H.264 结论套给新包。

不要只搜索某个 boot-arg 后立即修改配置。先读对应完整章节，了解该参数的前置条件和与其他层次的关系：

| 当前目标 | 优先阅读 | 相关工具 |
| --- | --- | --- |
| 新装 macOS | 01 硬件、03 身份、02 安装 | configure.py、apple_media.py、EFI / Delivery 构建脚本 |
| GPU 有 PCI 但没 Metal | 04 驱动、06 验收 | BAR 脚本、原生 Metal 源码 |
| 显卡接管后没画面 | 05 远程、04 切换显示 | SSH / VNC listener、保留安装阶段显示入口 |
| 关机或重启挂住 | 05 电源、03 OpenCore | AppleSMC 服务检查、实际 EFI 配置 |
| RustDesk 无 H.264 / HEVC | 05 远程、06 编解码 | 原生 VideoToolbox 测试与第三方程序实现 |
| CPU 身份或序列号维护 | 03 身份、01 CPU | 本地 settings / 现有 EFI，不重新生成身份 |
| 公开 GitHub | 07 发布、本文件 | check_publication.py，人工检查历史 / 截图 |

脚本路径与章节链接见索引。读完脚本再执行；不要把 script 中的模板路径当作当前机器已经存在的文件。

## 区分四种证据

1. **参考实机结果**：本仓库 2026-10-09 的记录，版本和硬件固定。可以据此选择排查方向，不能写成本次现场已验证。
2. **当前机器结果**：本次连接后实际得到的版本、状态、日志、像素测试、重启 / 关机结果。记录命令、时间和范围；敏感原始文件保留在私有位置。
3. **配置或源码推断**：例如某个 boot-arg 的设计作用、驱动设备表中的型号、QEMU 的 CPUID 计算。标为推断，继续用实际结果确认。
4. **未知 / 未通过**：没有测试的版本、HEVC 硬编码错误、长时间稳定性、其他 GPU、Apple ID 服务。保留这个标签，不因系统报告“支持”而改成通过。

对于这份基线，Metal 小规模三项和 H.264 短片段通过；HEVC 软件编码 → 硬件解码通过；**HEVC 硬件编码 API 虽成功，解码后的像素错误**。这个差别是判断编码能力的核心。

## 用分层模型理解机器

| 层次 | 主要状态 | 典型故障 |
| --- | --- | --- |
| BIOS / PCI 资源 | VT-d、Above 4G、IOMMU、MMIO、BAR1 | 无直通组、BAR 扩容失败 |
| Unraid / VFIO / QEMU | 设备归属、VM XML、磁盘、PCIe root port、OVMF | 设备占用、路径错误、虚拟机根本未启动 |
| OpenCore / EFI / NVRAM | 真正启动配置、版本、boot-args、SIP、身份 | 改错 EFI、Recovery 默认启动、KASLR 错误 |
| macOS 内核服务 | AppleSMC、kext、KC、framebuffer、accelerator | 双 SMC 关机递归、驱动不加载或不注册 |
| 用户态图形 / 视频 | NVMTL、Metal、VideoToolbox、像素正确性 | API 成功但内容错误、属性查询不兼容 |
| 远程客户端 | 网络、认证、共享授权、客户端编码实现 | VNC 不通、RustDesk 不提供编码器 |

按证据定位层次。比如客户机 `shutdown -h now` 在 SMC 回调里 panic，应修复客户机 SMC；把 `on_poweroff` 改来改去无法让客户机越过 panic。又比如 VNC TCP 端口不通，先检查网络与服务，不需要重装显卡驱动。

## 执行阶段与退出条件

### 阶段 0：确认范围和只读盘点

先确定用户是要输出资料、审查文件，还是已经授权真实安装 / 修复。已有系统先记录 VM 状态和原配置，不重新创建或抹盘。对于真实操作，取得用户允许使用的连接方式，不要求把密码提交到公开聊天或仓库。

需要盘点的最小信息：

- Unraid、内核、QEMU、libvirt 版本；VM 名称、状态、XML 和存储位置。
- CPU / GPU / 音频 ID、实际 BDF、IOMMU 组、当前驱动与占用进程。
- 是否已有 macOS、版本 / build、实际 EFI、NVRAM、网卡、远程入口。
- 显示器连接、Above 4G、BAR1 当前大小与支持掩码、可用空间。

原始 XML 和身份输出不能作为公开记录。只分享必要摘要。盘点明确后进入与现有状态匹配的阶段，而不是总从“重新安装”开始。

### 阶段 1：身份与安装介质

新 VM 才生成 macserial 配对、UUID 和 MAC。已有 VM 保留现有身份，包括 MAC 与 ROM 对应关系。使用一个 local/settings 驱动多个配置阶段，避免一次修复意外更换机器身份。

验证完整包和 Recovery 的固定 SHA256、容量、最终 SystemVersion。`macrecovery` 成功下载不保证返回 15.8.1；`BXDIFF50` 不是所有版本都可当作完整镜像解压。没有匹配固定资产时停止使用并核实版本，不能改校验值让未知文件通过。

退出条件：安装器版本明确，真正的 EFI 配置经 ocvalidate 1.0.5 通过，磁盘路径和每台 VM 独立的 NVRAM 已确认。

### 阶段 2：纯安装与远程入口

使用虚拟显示器和 VNC 安装，确认系统盘启动。安装结束移除临时 Recovery / Installer / Delivery 盘，保留可写 EFI。设置用户自己选择的账户密码，先确认 SSH / macOS VNC 可用。

退出条件：15.8.1 / 24H32 能从系统盘启动，远程入口有效，有完整冷备份。此时还不能说 RTX 加速已通过。

### 阶段 3：BAR 与驱动

正常关闭 VM，确认两 PCI 功能为 VFIO 且无人占用，再调整 BAR1。脚本必须支持失败后重新绑定，不能把 `virsh` 放进 libvirt hook。另行验证 Unraid 重启后的配置 / 钩子恢复，不把手动成功当成自动启动成功。

按第 04 章的固定 1.9.0 包校验并安装四个 kext / KC / 用户态组件，写入 GPU 阶段 EFI；原始 1.1.0 记录保留为历史证据。已有 VM 的升级另按第 09 章建立完整冷备份，保留其身份和既有 EFI。切换虚拟显示器前确认客户机远程服务；最终移除虚拟显示器，通过客户机 VNC 继续。

退出条件：BAR1 8GiB、驱动加载、NVIDIA Metal 设备可枚举、原生复制 / 计算 / 渲染通过。物理屏幕和远程画面也应实际确认。

### 阶段 4：功能与电源验收

运行原生视频测试，同时看 status、硬件标志、帧数和像素 MAE。不要只检查退出码或编码器名单。分别测试客户机主动关机与重启，检查 QEMU 退出 / SSH 恢复及 GPU 再次可用。

SMC 预期一个 AppleSMC 服务，VirtualSMC IOService 为零；kext 仍加载不构成重复服务证据。CPU 按 hw.physicalcpu / logicalcpu 验证 10 / 20，不追求修饰 ES 名称。

退出条件：形成带范围的结果清单、已知失败项、最后完整冷备份。没有通过的功能照实保留。

## 不要再走的试验路径

- 不用 `virsh destroy` 或自动断电假装修好了 macOS 关机。
- 不把 `ports=15` 当成增加 USB 端口的正确方式；本例 XHCI `ports=4`。
- 不因为 UUID 字符串不同就换身份；XNU 派生与字节序需要分别理解。
- 不复制物理机的 iGPU / 音频 / 网卡 DeviceProperties 猜测路径。
- 不为 ES CPU 名称加入已经失败的 RestrictEvents / ProcessorType 试验。
- 不凭“Metal 3”宣布 HEVC 编码、DRM、所有应用或其他 RTX 型号成功。
- 不将不同时间点的系统盘、EFI、NVRAM随意混用。

## 维护与交接

每次结束给下一位 AI 留以下摘要，真实身份和密码只写私有文件路径，不写值：

```text
任务范围：用户当前授权目标和限制
环境：硬件 / 各层软件版本；与参考基线的差异
当前阶段：正在运行或停止；已验证的远程入口
本次修改：配置位置、修改原因、前后差别
验证：命令与结果、测试范围，不能把静态检查写成实机测试
未解决：失败现象、错误码、尚未验证项
恢复点：私有冷备份位置与摘要检查结果
下一步：有证据支持的一个动作及成功标准
发布状态：隐私检查、是否提交 / 推送，原始文件仍保持私有
```

对大日志先提取关键段，保留原始日志的私有位置。使用者已有代理时，网络受阻优先按其指定代理重试；不要把本机 loopback 地址复制到另一台服务器后假定同一代理仍存在。

更新教材时同时维护对应章节和 `ai/knowledge.json`，避免与实测摘要矛盾。新测结果放新的日期文件，不覆盖旧基线冒充同一轮测试。

本地工作区：

```text
请先读取仓库根目录 AGENTS.md、docs/AI-GUIDE.md、ai/knowledge.json
和 results/observed-2026-10-09.json，再读取与任务相关的完整章节及脚本。
本次目标是：[填写安装、排障、审查或文档维护目标]。
先区分参考实测与当前机器状态；已有 VM 保留身份和可用配置。
在已授权范围内完成工作，按章节建立恢复点并验证，不重复询问已有授权。
不要宣称 HEVC 硬件编码或所有 RTX 全功能支持已通过。
结束时给出本次修改、实际验证、未解决项和下一步交接。
```

给只能联网阅读的 AI：

```text
请访问 https://github.com/dixtdf/unraid-macos-rtx3060，先读取根目录 AGENTS.md，按其中顺序

随后处理我的任务：[填写目标和已有环境]。缺少必要环境信息时先做可完成的
准备和只读核查，并明确指出哪一步依赖这些信息。
```
